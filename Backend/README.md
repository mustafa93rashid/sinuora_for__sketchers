# Sinuora Backend

خادم Node.js / Express 5 / Mongoose لإدارة المنتجات والأصناف والمخزون والطلبات والمستخدمين.

## التشغيل

1. ثبّت الحزم باستخدام `npm ci` على إصدار Node.js متوافق مع الحزم المثبتة (Node.js 22.12 أو أحدث).
2. انسخ `.env.example` إلى `.env` واضبط القيم. لا تنسخ مثال الإعدادات فوق ملف أسرار موجود.
3. استخدم MongoDB Replica Set أو Sharded Cluster؛ لا يدعم التطبيق standalone لأن عمليات المخزون والطلبات تعتمد على معاملات متعددة المستندات.
4. شغّل `npm start`. يتحقق الخادم من الإعدادات ودعم المعاملات ويبني الفهارس قبل فتح المنفذ. لا يحذف البيانات أو الفهارس الموجودة تلقائياً.
5. لإنشاء أول superadmin فقط، اضبط متغيرات `SUPER_ADMIN_EMAIL` و`SUPER_ADMIN_PASSWORD` ثم شغّل `npm run seed:superadmin`.

`GET /api/health` يعيد 200 عند اتصال قاعدة البيانات و503 عند انقطاعها. استيراد `src/app.js` في الاختبارات لا يشغّل الخادم أو يتصل بقاعدة البيانات؛ يمكن استخدام `app` أو `start` أو `stop` المصدّرة منه.

## الإعدادات

- `MONGODB_URL`: رابط قاعدة البيانات مع إعداد Replica Set عند الحاجة.
- `JWT_SECRET_KEY` و`REFRESH_JWT_SECRET_KEY`: قيمتان مختلفتان بطول 32 حرفاً على الأقل.
- `JWT_ACCESS_EXPIRES_IN=15m` و`JWT_REFRESH_EXPIRES_IN=7d`: مدد بوحدات s/m/h/d.
- أحد `DASHBOARD_URL` أو `FRONTEND_URL` مطلوب في الإنتاج لإنشاء روابط التفعيل وإعادة التعيين. في وضع التطوير يمكن استخدام الإعداد القائم `DASHBOARD_URL_LOCAL` عند غيابهما. يمكن تعيينهما معاً إذا اختلفت الوجهتان.
- عناوين CORS الإضافية الاختيارية: `WEBSITE_URL`, `DASHBOARD_URL_LOCAL`, `WEBSITE_URL_LOCAL`, `CLIENT_URL`, `VERCEL_URL`؛ استخدم روابط كاملة تتضمن البروتوكول.
- `TRUST_PROXY_HOPS=0` افتراضياً. عيّن العدد الفعلي للوسطاء الموثوقين أمام التطبيق؛ لا تضع 1 إن كان الخادم مكشوفاً مباشرة.
- إعدادات SMTP وCloudinary مطلوبة كما في `.env.example`.
- `NODE_ENV=production` يفعّل Secure وSameSite=None للكوكيز؛ يلزم HTTPS. التطوير المحلي يستخدم Lax.

## عقد API الأساسي

جميع المسارات التشغيلية تحت `/api/v1` وتتطلب المصادقة. الرموز محفوظة في HttpOnly cookies، وAccess Token مقبول أيضاً عبر Bearer.

| العملية | المسار | متطلبات إضافية |
|---|---|---|
| إنشاء طلب | POST `/orders` | `Idempotency-Key` |
| تعديل طلب | PATCH `/orders/:id` | حالة New أو Preparing |
| إلغاء | PATCH `/orders/:id/cancel` | `reason`، قبل الإرسال |
| تجهيز | PATCH `/orders/:id/prepare` ثم `/prepared` | مدير |
| إرسال | PATCH `/orders/:id/dispatch` | حالة Prepared |
| تسليم | PATCH `/orders/:id/deliver` | يحسم كل الكمية المتبقية |
| إرجاع | POST `/orders/:id/returns` | `Idempotency-Key`, items, reason |
| إدخال مخزون | POST `/inventory/variant/:variantId/add` | مدير، `Idempotency-Key`, quantity, reason |
| تسوية مخزون | PATCH `/inventory/variant/:variantId/adjust` | مدير، `Idempotency-Key`, newQuantity, reason |
| تغيير البريد | POST `/users/profile/email-change/request` | newEmail وcurrentPassword، ثم verify بالرمز |
| تفعيل الحساب | POST `/users/activate-account` | token وpassword وconfirmPassword |

المفتاح 8–128 حرفاً من الحروف الإنجليزية والأرقام والشرطة والشرطة السفلية. استخدم مفتاحاً جديداً لعملية جديدة، ونفس المفتاح مع نفس المحتوى عند إعادة المحاولة. اختلاف المحتوى مع نفس المفتاح يرجع 409.

مثال إنشاء طلب:

```json
{
  "customer": { "name": "اسم الزبون", "phone": "07700000000", "address": "بغداد" },
  "items": [{ "variant": "0123456789abcdef01234567", "quantity": 2, "unitPrice": 35000 }],
  "deliveryFee": 5000,
  "discount": 0,
  "notes": "ملاحظة"
}
```

الأسعار والكميات أعداد صحيحة آمنة؛ الأسعار في الوحدة النقدية الموحدة بين الواجهة والخادم. `deliveredAmount` و`returnedAmount` قيمة القطع فقط، ولا يمثلان تسوية نقدية لرسوم التوصيل أو الخصم. لا ينفذ الخادم دفعاً أو رد أموال.

## الصلاحيات

| الدور | الطلبات | المنتجات والمخزون |
|---|---|---|
| superadmin | جميع العمليات | جميع العمليات وإدارة المستخدمين |
| manager | جميع العمليات | تعديل الكتالوج والمخزون ورؤية التكلفة والحركات؛ قراءة قائمة المستخدمين |
| saler | إنشاء وقراءة وتعديل وإلغاء وتسليم وإرجاع طلباته فقط | قراءة الكتالوج والأرصدة دون تكلفة أو سجل الحركات |
| follow-up | قراءة حالات Prepared وما بعدها، والتسليم والإرجاع | قراءة الكتالوج والأرصدة دون تكلفة أو سجل الحركات |

أرشفة المنتج عبر `/archive` واستعادته عبر `/restore`؛ `isActive` غير مسموح في التعديل العام. لا يمكن تغيير لون/قياس/SKU لصنف سبق استخدامه. المرتجع `DAMAGED` يُسجل في `quarantinedQuantity` ولا يصبح متاحاً للبيع.

## الاختبارات

```powershell
npm test
npm run test:integration
```

`npm test` يشغّل اختبارات الوحدة. أمر التكامل هو فحص الإصدار الكامل ولا يسمح بتخطي قاعدة الاختبار. يشغّل قاعدة محلية مؤقتة على منفذ عشوائي؛ لا يستخدم `MONGODB_URL` أو `.env` ولا يرسل بريداً أو صوراً إلى خدمات حقيقية. يبقى مجلد قاعدة الاختبار المؤقت وسجله للتشخيص، وتُوقف عملية mongod بعد الاختبار.

يحاول `test:integration` تحديد مسار `mongod` تلقائياً (تثبيت Windows المعتاد تحت `C:\Program Files\MongoDB\Server\<version>\bin\mongod.exe`، أو المسارات المعتادة على Linux/macOS). إن فشل التحديد التلقائي، أو لتحديد مسار مخصص، يمكن ضبطه يدوياً:

```powershell
$env:MONGOD_BINARY = 'C:\Program Files\MongoDB\Server\8.2\bin\mongod.exe'
npm run test:integration
```

ملاحظة: لا توجد خطوط CI حالياً تُشغّل `test:integration` تلقائياً على كل Pull Request (راجع قسم الجاهزية للنشر)؛ يجب تشغيله يدوياً قبل أي دمج يغيّر منطق الطلبات أو المخزون أو المصادقة.

## ملاحظات النشر

- الجلسات القديمة تحتاج تسجيل الدخول بعد التحديث. الحساب يحتفظ بجلسة واحدة كما في التصميم الأصلي.
- مهام حذف الصور وإشعارات الأمان محفوظة في `maintenancejobs` وتُعالج كل 30 ثانية مع إعادة المحاولة. راقب المهام المتأخرة و`lastError`.
- الـrate limiter الحالي في ذاكرة العملية. عند النشر عبر عدة عمليات، يلزم مخزن مشترك للمحددات وSocket.IO adapter مناسب لضمان تنسيقها؛ فحص Socket الدوري يغلق الجلسات المبطلة خارج العملية خلال خمس ثوانٍ.
- الواجهة يجب أن تعرض النصوص بترميز آمن، ولا تستخدم HTML خاماً من حقول المستخدم. الخادم لا يغيّر كلمات المرور أو النصوص بإزالة الوسوم.
- بيانات المتجر القديمة لم تُرحَّل تلقائياً. راجع الأسعار الكسرية والبيانات المتكررة قبل التشغيل؛ لا تُعدّل الأرصدة بالتخمين.

راجع `docs/review-fixes.md` لتفاصيل إصلاحات المراجعة والتوافق مع البيانات القديمة.

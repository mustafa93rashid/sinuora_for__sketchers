# Orders — المرحلة الأولى

## ما تم تنفيذه

- إنشاء طلب متعدد العناصر بحالة `New`، مع حجز المخزون وتسجيل `RESERVE` وسجل الحالة داخل Transaction واحدة.
- `OrderItem` مستند فرعي داخل `Order` وله `_id` ثابت يستخدم في `InventoryTransaction.orderItem`. يحفظ اسم المنتج والموديل واللون والقياس وSKU وسعر البيع وقت الطلب، مع مراجع المنتج والـVariant.
- `OrderStatusHistory` مجموعة مستقلة لحفظ الفاعل والوقت والسبب والحالة السابقة والجديدة.
- منع تكرار الإنشاء بمفتاح يرسله العميل: فهرس فريد على `createdBy + idempotencyKey`، وبصمة للطلب بعد التطبيع. Transactions وحدها لا تمنع إعادة إرسال عملية ناجحة.
- إلغاء الطلب قبل الإرسال، مع فك الحجز مرة واحدة والاحتفاظ بالطلب وسجل حالاته. الإلغاء النهائي لا يحتاج مفتاحاً آخر؛ إعادة الإلغاء تُرجع الطلب الملغى دون تحرير جديد أو استبدال السبب الأصلي.
- عرض الطلبات وتفاصيلها وسجل الحالات ضمن صلاحيات المستخدم.

## تغييرات البنية وسببها

`inventory.helper` يحتفظ بأسماء عملياته السابقة، ويقبل `session` اختيارياً. عند تمرير Session يجب أن تكون داخل Transaction فعالة. إذا لم تُمرر، يفتح Transaction خاصة به. كل تحديث وسجل حركة ينفذان معاً؛ إضافة المخزون تستخدم `$inc`، والتعديل يستخدم شرطاً ذرياً يمنع النزول تحت المحجوز. أزيل أسلوب القراءة ثم الحفظ لتجنب فقدان تحديثات متزامنة.

`transaction.helper` مشترك. لا يوجد `Promise.all` داخل Transaction ولا اتصالات خارجية أو إشعارات داخل callback المعرض لإعادة المحاولة.

`app.js` يسجل `/api/v1/orders`، ويتحقق من دعم Transactions ويبني فهارس الطلبات قبل الاستماع للطلبات. لا يتم تغيير أسماء حقول ProductVariant أو InventoryTransaction ولا أسماء الأدوار أو ترحيل بيانات قديمة. لا توجد حزم إضافية.

مبالغ الطلبات الجديدة تستخدم `Decimal128`، وتدخل وتخرج عبر API كنصوص عشرية، مع حساب المجموع باستخدام BigInt لتجنب أخطاء الكسور. أسعار Product القديمة لا تتغير، ولا يتم اختيار سعر تلقائي منها. الحدود التقنية: 18 خانة صحيحة و12 عشرية لكل سعر، وبحد أقصى 34 خانة للمجموع؛ حتى 100 عنصر ومليون قطعة لكل عنصر.

## الحدود والقرارات غير المحسومة

- `itemsSubtotal` هو مجموع القطع فقط؛ ليس المبلغ النهائي المستحق ولا المبلغ المسترد. لا توجد سياسة عملة أو رسوم توصيل أو خصومات أو استرداد نقدي مفترضة. حقول مثل `deliveryFee` و`discount` و`total` تُرفض، وكذلك حقول الحالة والموظف والمخزون التي يتحكم بها الخادم.
- تكرار Variant داخل الطلب يُرفض؛ على العميل جمع كميته في عنصر واحد. سعر الوحدة يُدخل صراحة كنص، مثل `"35000"`.
- نطاق الصلاحيات الأولي: Super Admin ينشئ ويعرض ويلغي؛ Manager يعرض؛ saler ينشئ ويعرض طلباته فقط؛ follow-up يعرض حالات Prepared وما بعدها. الإلغاء محصور بـSuper Admin لحين توسيع الصلاحيات صراحة.
- الحالات المعتمدة موجودة في Model: New → Preparing → Prepared → Out For Delivery → Delivered، ثم/أو Returned وPartially Returned حسب عمليات الإرجاع. وجودها في enum لا يعني أن انتقالاتها منفذة في المرحلة الأولى.
- لا يوجد endpoint لتعديل العناصر أو تغيير الحالات أو الشحن أو التسليم أو الإرجاع بعد. `returnedQuantity` تجهيز للمرحلة القادمة، ولا يُقبل من العميل.
- دوال `confirmSale` و`returnStock` الداخلية تدعم Session، لكنها ليست واجهات طلبات ولا تمنع التكرار بمفردها؛ المرحلة التالية تربطها بانتقال حالة/سجل إرجاع محدد ومفتاح عملية داخل Transaction.
- الإشعارات والتقارير وصفحة Returns في مراحل لاحقة. لا يتم إرسال إشعارات مؤقتة قد تضيع قبل اعتماد آلية الحفظ والإرسال.

## API

| الطريقة | المسار | الوظيفة |
|---|---|---|
| POST | `/api/v1/orders` | إنشاء وحجز، مع `Idempotency-Key` |
| GET | `/api/v1/orders?page=1&limit=20&status=New` | قائمة حسب الصلاحيات |
| GET | `/api/v1/orders/:id` | الطلب وسجل حالاته |
| PATCH | `/api/v1/orders/:id/cancel` | إلغاء قبل الإرسال بواسطة Super Admin |

مثال جسم الإنشاء (استبدل معرّف Variant بمعرّف موجود):

```json
{
  "customer": { "name": "اسم الزبون", "phone": "07700000000", "address": "بغداد" },
  "items": [{ "variant": "0123456789abcdef01234567", "quantity": 2, "unitPrice": "35000" }],
  "note": "ملاحظة اختيارية"
}
```

أرسل `Idempotency-Key: checkout-unique-0001` مع بيانات المصادقة المعتادة. المفتاح 8–128 حرفاً من الأحرف اللاتينية والأرقام و`_` و`-`. حافظ على نفس المفتاح عند إعادة المحاولة لنفس العملية؛ طلب جديد فعلياً يحتاج مفتاحاً جديداً.

الإنشاء يعيد `201`، والإعادة المتطابقة `200` مع `replayed: true`، والمفتاح نفسه مع بيانات مختلفة `409`. الرد يحتوي `data.order`. المفتاح والبصمة لا يظهران في الرد. إعادة إنشاء طلب سبق إلغاؤه بنفس المفتاح تعيد الطلب الملغى ولا تعيد حجزه.

جسم الإلغاء: `{ "reason": "طلب الزبون الإلغاء" }`. الطلب المُرسل لا يمكن إلغاؤه بهذا المسار. الاسترجاع سيستخدم مساراً منفصلاً في المرحلة التالية.

## تشغيل واختبار

يشترط MongoDB Replica Set أو Atlas أو Sharded Cluster. التشغيل على standalone يتوقف برسالة واضحة؛ ينطبق ذلك أيضاً على عمليات المخزون القديمة بعد دمج الحركات في Transactions. لا تستخدم اختبارات التكامل قاعدة المتجر أو `MONGODB_URL`؛ تبدأ عملية mongod جديدة على منفذ مؤقت بمجلد بيانات اختبار مستقل، ثم توقفها. يبقى المجلد المؤقت وسجله للتشخيص.

```powershell
$env:MONGOD_BINARY = 'C:\Program Files\MongoDB\Server\8.2\bin\mongod.exe'
npm run test:orders
```

بدون `MONGOD_BINARY` تنفذ اختبارات الوحدة فقط وتظهر اختبارات التكامل كمتجاوزة، وهذا لا يكفي للتحقق من التزامن.

## المراحل التالية

1. انتقالات Preparing وPrepared وOut For Delivery مع سجل الفاعل، وخصم `stockQuantity` و`reservedQuantity` معاً عند الإرسال فقط.
2. Delivered وReturn مستقل يدعم عناصر وكميات جزئية، وإعادة المخزون فور تسجيل الإرجاع، ومنع تجاوز الكمية المرسلة أو تكرار نفس الإرجاع بمفتاح فريد. تحديد حالة بقية العناصر عند الإرجاع الجزئي قبل بناء واجهته.
3. مراجعة حماية تغيير هوية Variant وأرشفة المنتجات بالتزامن مع الطلبات، ثم تعديل الطلبات، والصلاحيات الإضافية، والإشعارات الدائمة والتقارير والسياسات المالية بعد حسمها.

المراجع التقنية: [Mongoose Transactions](https://mongoosejs.com/docs/transactions.html)، [MongoDB Transactions](https://www.mongodb.com/docs/manual/core/transactions/).

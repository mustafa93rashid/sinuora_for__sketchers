# إصلاحات المراجعة — 2026-10-26

هذا الملف يوثق السلوك الحالي. تفاصيل إعداد البيئة وعقد الواجهة في README.md.

## الطلبات والصلاحيات

- إنشاء الطلب وتعديله يمران من controller إلى order.helper، مع استخراج المعرف من المسار ومفتاح العملية من الترويسة وإرسال استجابة HTTP.
- superadmin وmanager يستطيعان إنشاء وعرض وتعديل وإلغاء وتجهيز وإرسال وتسليم وإرجاع الطلبات.
- saler ينشئ ويعرض ويعدل ويلغي ويسلّم ويرجع طلباته فقط؛ لا يجهز أو يرسل.
- follow-up يعرض حالات Prepared وما بعدها، ويسلّم ويرجع؛ لا ينشئ أو يعدل أو يلغي.
- تكلفة المنتج وتكلفة الطلب التاريخية تظهران فقط لـsuperadmin وmanager. سجل حركات المخزون التفصيلي محصور بهذين الدورين.
- فلترة الاستعلامات تستخدم req.validatedQuery المستخرج من matchedData، ولا تعتمد على تغيير getter الخاص بـreq.query في Express 5.
- أسعار المنتج والطلب أعداد صحيحة آمنة وغير سالبة، بنفس الوحدة النقدية المتفق عليها في الواجهة. لا يجري تقريب أسعار قديمة أو تحويلها تلقائياً.

## المخزون والتزامن

- الإنشاء يحجز الكمية، والإلغاء يفك الحجز، والإرسال يخصم الرصيد الفعلي والمحجوز معاً.
- حجز المخزون وعمليات إدخال المخزون وتعديل رصيده وعمليات الأرشفة تشترك في كتابة إصدار داخلي على مستند المنتج. ذلك يفرض تعارض كتابة عند تزامن الأرشفة والحجز؛ قراءة المنتج داخل transaction وحدها لا تكفي.
- أرشفة variant تستخدم شرط reservedQuantity = 0 داخل معاملة. مسار تعديل المنتج العام يرفض isActive ويوجه إلى archive/restore.
- اللون والقياس وSKU يمكن تصحيحها قبل استخدام الـvariant فقط. بعد وجود مخزون أو حركات أو طلبات تصبح الهوية ثابتة. الفحص يشمل البيانات القديمة التي لا تحتوي identityLocked.
- عمليات HTTP لإضافة المخزون وتعديله تحتاج Idempotency-Key. الفهرس الفريد يجمع الموظف والـvariant ونوع الحركة والمفتاح. إعادة نفس المحتوى لا تنشئ حركة جديدة، وتغيير المحتوى مع نفس المفتاح يرجع 409. الاستجابة عند الإعادة تعرض الرصيد الحالي.
- DAMAGED يسجل QUARANTINE_RETURN ويزيد quarantinedQuantity فقط؛ لا يدخل stockQuantity ولا availableQuantity. سجل الإرجاع يوضح restockedQuantity وquarantinedQuantity. بقية أسباب الإرجاع تعيد القطع إلى المخزون كما في العقد السابق.
- لا يوجد تحرير تلقائي للتالف إلى الرصيد القابل للبيع. يلزم مسار أعمال مستقل للفحص والتصريف إذا احتاجه المتجر.

## الحسابات والجلسات

- كل Access/Refresh Token يحتوي type وver وjti عشوائياً ووقت انتهاء. الإصدار مرتبط بـtokenVersion في المستخدم.
- تسجيل الدخول يستبدل الجلسة السابقة، بما يتوافق مع تخزين Refresh Token واحد لكل حساب. الخروج وتغيير كلمة المرور أو البريد وتعديل الدور/الحالة والحذف المنطقي تبطل الجلسات السابقة.
- تدوير Refresh Token يتم بتحديث شرطي ذري. الطلب المتزامن الخاسر لا يمسح رمز الجلسة الفائزة.
- إعادة تعيين كلمة المرور والتفعيل وتأكيد الرموز تستهلك الرمز بتحديث شرطي. رموز البريد وتغيير كلمة المرور محدودة بخمس محاولات لكل إصدار رمز، إضافة إلى محددات الطلبات.
- تغيير البريد يحتاج currentPassword ثم رمزاً إلى العنوان الجديد. نجاحه يسجل إشعاراً دائماً إلى العنوان القديم داخل المعاملة نفسها، ويبطل الجلسات.
- كلمات المرور والرموز لا تمر عبر تنظيف HTML أو trim عام. الواجهة مسؤولة عن العرض النصي الآمن؛ قوالب البريد تهرّب القيم في سياق HTML.
- حذف المستخدم منطقي عبر deletedAt/isActive. المراجع التاريخية تبقى قابلة للعرض. البريد يبقى محجوزاً ولا يعاد تخصيصه لحساب جديد تلقائياً.
- منع تغيير المستخدم لدوره/حالته يستخدم _id. تعديلات المديرين تتشارك قفلاً في MongoDB وتعيد التحقق من المدير المنفذ داخل المعاملة.
- Socket.IO يطرد جلسات المستخدم محلياً فور الإبطال، ويغلق الاتصال عند انتهاء الرمز، ويعيد التحقق كل خمس ثوانٍ للحالات المتغيرة خارج العملية الحالية. origin موحد مع HTTP ويُفحص أيضاً لاتصالات WebSocket.

## الصور والعمليات الخارجية

- يحجز الرفع publicId فريداً ويسجل مهمة staged قبل الاتصال بـCloudinary.
- ربط الصور الجديدة وحفظ المستند وطلب حذف الصور القديمة يحدثان في معاملة MongoDB واحدة، بعد انتهاء الرفع.
- فشل الحفظ أو الرفع الجزئي يترك مهام حذف قابلة لإعادة المحاولة، ويحافظ على الصورة السابقة المرتبطة بالمستند.
- العامل الخلفي يعالج maintenancejobs كل 30 ثانية، مع حجز المهمة وإعادة المحاولة بتأخير متزايد. يتحقق من أن الصورة غير مستخدمة قبل حذفها.
- حذف Cloudinary يقبل ok/not found. إشعارات البريد الدائمة تملك تسليماً من نوع at-least-once؛ قد يتكرر إشعار عند تعطل العملية بعد الإرسال وقبل تأكيد المهمة.
- في حال انقطاع الخدمة، تبقى المهام محفوظة وتُستأنف عند التشغيل التالي. راقب pending/processing والحقول attempts/lastError.

## توافق البيانات القديمة

- لا تنفذ الإصلاحات ترحيلاً تلقائياً أو تعديلاً لأرصدة المتجر. غياب tokenVersion يعامل كالإصدار صفر، بينما الرموز القديمة التي لا تتبع العقد الجديد تُرفض ويحتاج المستخدم تسجيل الدخول.
- لا تعاد صياغة كلمات المرور القديمة. كلمة المرور التي كانت تُنظف سابقاً تطابق القيمة التي حُفظت فعلاً؛ استخدم إعادة التعيين عند الحاجة.
- لا تُستنتج كميات تالفة قديمة من السجلات ولا يعاد تصنيفها تلقائياً.
- أسعار قديمة كسرية أو غير آمنة تحتاج تصحيحاً مقصوداً قبل حفظها/استخدامها؛ لا يتم التقريب بصمت.
- إنشاء الفهارس عند التشغيل قد يفشل إذا كانت بيانات قديمة متكررة. لا يحذف التطبيق فهارس أو مستندات لإخفاء المشكلة.
- تظهر التغييرات التالية للواجهة: currentPassword لتغيير البريد؛ Idempotency-Key لإضافة/تعديل المخزون؛ رفض isActive في تعديل المنتج؛ 403 لسجل المخزون عند الأدوار المحدودة؛ حقول الحجر الجديدة؛ إعادة الدخول بعد إبطال الجلسة.

## التحقق

اختبارات الوحدة تغطي تحقق المدخلات وعقد JWT وحفظ الأسرار وإعدادات التشغيل. اختبارات التكامل تشغل mongod جديداً بمعرف Replica Set ومنفذ ومجلد مستقلين، وتشمل واجهات HTTP الحقيقية وSocket.IO، والتزامن، وrollback، والجلسات، وملفات المستخدم القديمة، وصوراً وبريداً محاكيين دون اتصال خارجي.

شغّل npm run test:integration بعد تعيين MONGOD_BINARY؛ يفشل الأمر إذا لم يتوفر الملف بدلاً من اعتبار تخطي اختبارات التكامل نجاحاً.

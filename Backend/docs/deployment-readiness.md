# قائمة الجاهزية للنشر (Production Readiness Checklist)

**الحالة:** هذا المستند توثيقي بالكامل. لم يُنفَّذ أي نشر فعلي ولم تُعدَّل أي بنية تحتية أو بيانات إنتاجية كجزء من كتابته (ضمن المرحلة 7 من مشروع معالجة نتائج التدقيق). يجمع هذا المستند خيوطاً موثّقة سابقاً في `README.md` و`docs/backup-disaster-recovery.md` و`docs/review-fixes.md` في قائمة فحص واحدة قابلة للتنفيذ، ويضيف ما كان ناقصاً: تكامل مستمر (CI) فعلي، وتأكيد صريح لهدف الاستضافة.

---

## 1. تأكيد بيئة الاستضافة (قرار عمل مطلوب — لم يُحسم بعد)

لا يحدد هذا المستودع حالياً أي ملف بنية تحتية (`Dockerfile`, `vercel.json`, إلخ) ولا أي متغير بيئة يُثبت نوع الاستضافة الفعلي. هذا **قرار عمل، لا تقني**، ويجب تأكيده قبل أي نشر فعلي:

- [ ] **الخادم الخلفي (Backend)**: هل سيُستضاف على عملية Node.js طويلة الأمد (VPS، أو منصة PaaS مثل Render/Railway/Fly.io)، أم ضمن بيئة serverless؟ **تنبيه مهم**: التطبيق يحتفظ بحالة داخل العملية (rate limiter في الذاكرة، Socket.IO، مهام الصيانة الدورية كل 30 ثانية) ويتطلب MongoDB replica set للمعاملات — هذا يناسب عملية طويلة الأمد تقليدية أكثر من دوال serverless قصيرة العمر. انظر قسم "ملاحظات النشر" في `README.md` السطر 89 وما بعده.
- [ ] **قاعدة البيانات**: MongoDB Atlas أم self-hosted replica set؟ يحدد هذا أي قسم من `docs/backup-disaster-recovery.md` ينطبق فعلياً (يحتوي المستند كلا الاحتمالين؛ يجب حذف غير المنطبق بعد التأكيد).
- [ ] **الواجهة الأمامية (Frontend)**: استضافة ثابتة (static hosting) مع إعادة توجيه `/api` إلى الخادم الخلفي عبر reverse proxy، كما هو موثّق في `Frontend/README.md` السطر 33. يجب تأكيد مزوّد الاستضافة الفعلي ليُضبط الـ reverse proxy وHTTPS والأصول المسموحة (CORS origins) بشكل صحيح.
- [ ] عند التأكيد: حدّث `Backend/.env` الفعلي في بيئة الإنتاج بالقيم الصحيحة لـ `DASHBOARD_URL`/`FRONTEND_URL`/`WEBSITE_URL` (وليس `DASHBOARD_URL_LOCAL` الخاص بالتطوير فقط).

---

## 2. التكامل المستمر (CI) — تم إنشاؤه ضمن هذه المرحلة، يحتاج تأكيد تشغيل فعلي

كانت هذه فجوة موثّقة صراحة في `README.md` ("لا توجد خطوط CI حالياً تُشغّل test:integration تلقائياً على كل Pull Request"). أُضيف `.github/workflows/ci.yml` يشغّل تلقائياً على كل Pull Request وPush إلى `main`:

- **Backend**: `npm ci` → `npm test` (اختبارات الوحدة) → تثبيت `mongod` عبر مستودع MongoDB الرسمي لـ apt → `npm run test:integration` (الاختبار التكاملي الكامل على replica set مؤقت ومعزول، بدون أي اتصال بخدمات حقيقية أو أسرار).
- **Frontend**: `npm ci` → `npm test` → `npm run build`.

**لا يحتاج أي من هذين المسارين إلى أي سر (secret) مُدار عبر GitHub** — جميع ملفات الاختبار تُعرّف قيمها الخاصة بمفاتيح JWT وغيرها داخلياً (راجع التحقق التفصيلي أدناه)، ولا تُحمَّل بيانات `.env` الفعلية في بيئة CI.

- [ ] **لم يُختبر هذا الملف فعلياً على GitHub بعد** (لم يُدفع أي التزام يحتوي عليه إلى الفرع البعيد كجزء من هذا التدقيق، التزاماً بقاعدة عدم الدفع دون إذن صريح). **يجب تشغيله مرة واحدة فعلياً بعد الدمج والتأكد من نجاحه قبل الاعتماد عليه كبوابة دمج إلزامية.**
- [ ] نقطة ضعف معروفة ومقصودة: مُثبَّت الإصدار `runs-on: ubuntu-22.04` (وليس `ubuntu-latest`) للمهمة الخلفية تحديداً، لأن مستودع MongoDB الرسمي لـ apt يُنشر حسب اسم إصدار Ubuntu ("jammy") وليس مضموناً التوافق التلقائي مع كل إصدار مستقبلي لـ `ubuntu-latest`. عند الرغبة بالترقية مستقبلاً، يجب أولاً تأكيد أن MongoDB نشرت مستودعاً مطابقاً للإصدار الجديد.
- [ ] بعد التأكد من نجاح أول تشغيل فعلي: يُنصح بتفعيل "Require status checks to pass before merging" في إعدادات الفرع `main` على GitHub (إجراء على نظام مشترك، يتطلب إذناً صريحاً منفصلاً لأنه يغيّر سياسة الدمج لكل المساهمين — لم يُفعَّل هنا).

## 3. قائمة فحص ما قبل أي نشر فعلي

- [ ] تشغيل `npm test` و`npm run test:integration` في `Backend`، و`npm test` و`npm run build` في `Frontend` — جميعها محلياً أو عبر CI (البند 2 أعلاه) قبل أي دمج أو نشر.
- [ ] مراجعة `docs/review-fixes.md` للتأكد من عدم وجود بيانات قديمة غير متوافقة مع إصلاحات هذا المشروع (أسعار كسرية، بيانات مكررة).
- [ ] تدوير بيانات اعتماد `superadmin` المزروعة عبر `npm run seed:superadmin` فور أول تسجيل دخول فعلي في الإنتاج — لا تُستخدم قيم بيئة التطوير نفسها.
- [ ] التأكد أن `NODE_ENV=production` مضبوط فعلياً (يُفعّل `Secure`/`SameSite=None` على الكوكيز ويتطلب HTTPS فعلياً من المتصفح — نشر بدون HTTPS فعلي سيكسر تسجيل الدخول في هذا الوضع).
- [ ] التأكد من قيم `JWT_SECRET_KEY` و`REFRESH_JWT_SECRET_KEY` الفعليتين في الإنتاج: مختلفتان، وبطول 32 حرفاً فعلياً على الأقل (يتحقق `src/config/startup.js` من هذا عند الإقلاع ويرفض البدء إن لم يتحقق الشرط — لا حاجة لتحقق يدوي إضافي، لكن يجب التأكد أن القيم الفعلية في بيئة الإنتاج ليست نفس قيم ملف `.env.example` أو بيئة التطوير).
- [ ] مراجعة قيود التوسع الأفقي الموثّقة في `README.md` (rate limiter في الذاكرة، Socket.IO) إن كانت الخطة تشغيل أكثر من نسخة (process) واحدة من الخادم في الإنتاج.
- [ ] نسخة احتياطية مؤكدة وفعلية (ليست نظرية) قبل أي ترحيل بيانات أو تغيير بنيوي — راجع `docs/backup-disaster-recovery.md`.

---

## 4. المراقبة بعد النشر

- `GET /api/health` يعيد 200 عند اتصال قاعدة البيانات و503 عند انقطاعها — نقطة بداية جيدة لأي فحص صحة خارجي (uptime monitor)، لكنه لا يتحقق من صحة maintenance jobs أو Socket.IO.
- راقب `maintenancejobs` (حذف الصور، إشعارات الأمان) وحقل `lastError` فيها كما هو موثّق في `README.md` — لا توجد تنبيهات آلية مُعدّة لتأخرها حالياً.

---

## ملاحظة ختامية

لا يتضمن هذا المستودع أي سكريبت نشر مؤتمت (لم يُنشأ أي سكريبت تنفيذي للنشر كجزء من هذا التدقيق). قائمة الفحص أعلاه مرجعية للتنفيذ اليدوي من فريق العمليات بعد حسم القرارات المعلّمة أعلاه.

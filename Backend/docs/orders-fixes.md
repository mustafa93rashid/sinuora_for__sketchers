# إصلاح Orders

تم الاعتماد على المشروع الحالي في `D:\Sinuora for sketchers\Backend`، وليس نسخة orders-phase1 القديمة.

## الصلاحيات

- superadmin وmanager: إنشاء، عرض، تعديل، إلغاء، تجهيز، إرسال، تسليم وإرجاع جميع الطلبات.
- saler: إنشاء وعرض وتعديل وإلغاء وتسليم وإرجاع طلباته فقط؛ لا تجهيز ولا إرسال.
- follow-up: عرض طلبات المتابعة وتأكيد التسليم والإرجاع؛ لا تعديل أو إلغاء أو تجهيز.
- بقيت routes بالنمط `[auth, role([...])]` و`asyncHandler`؛ كانت صلاحياتها صحيحة، والتعارض داخل helper هو الذي أُصلح. بقي controller بأسمائه الحالية.

## المخزون ودورة الطلب

New → Preparing → Prepared → Out For Delivery → Delivered.

الإنشاء يحجز الكميات. الإلغاء قبل الإرسال يفك الحجز. الإرسال يخصم الكمية الفعلية والمحجوزة معاً. الإرجاع بعد الإرسال يعيد الفعلي إلى نفس Variant.

التعديل متاح في New وPreparing، ويحتفظ بمعرّفات العناصر الموجودة. الحركات الناتجة عن إضافة عنصر جديد ترتبط الآن بمعرّفه الصحيح. يسجل التعديل الموظف في updatedBy وفي التاريخ كحدث بنفس الحالة مع السبب Order updated.

الإرجاع متاح من Out For Delivery وDelivered وPartially Returned. الحد الأعلى لكل عنصر هو dispatchedQuantity - returnedQuantity. بعد إرجاع قطع مسلّمة، تنخفض deliveredQuantity لتعبّر عن القطع المسلّمة التي لم ترجع.

كل إرجاع مستقل له OrderReturn؛ يمكن تسجيل عدة إرجاعات جزئية. الحالة Returned ونوع FULL يعنيان أن مجموع الإرجاعات أكمل جميع الكميات المرسلة، حتى لو كانت العملية الأخيرة صغيرة. الإرجاع الجزئي لا يثبت تسليم الباقي. `/deliver` يؤكد الباقي، مع بقاء الحالة Partially Returned عند وجود مرتجعات. followUpCompleted يعكس عدم وجود قطع تنتظر حسم التسليم أو الإرجاع.

OrderReturn والمخزون والطلب وسجل الحالة تنفذ داخل Transaction واحدة. optimisticConcurrency يمنع حفظ نسخة قديمة من الطلب، وفهارس idempotency تُجهز قبل الإنشاء والإرجاع حتى عندما يكون autoIndex معطلاً. لا يجري حذف فهارس قائمة تلقائياً. الجلسة الممررة إلى مساعد المخزون يجب أن تكون داخل Transaction فعالة.

## عقد API المؤثر

إنشاء الطلب وPOST `/api/v1/orders/:id/returns` يحتاجان ترويسة `Idempotency-Key` بطول 8–128 من الأحرف الإنجليزية والأرقام و`_` و`-`. يستخدم العميل مفتاحاً جديداً لكل عملية فعلية، ونفس المفتاح عند إعادة المحاولة. تكرار المفتاح ببيانات مختلفة يرجع 409. مفتاح الإرجاع فريد داخل الطلب، ومفتاح الإنشاء فريد للموظف. المفتاح والبصمة لا يظهران في الاستجابات.

مثال إرجاع:

```json
{
  "items": [{ "orderItem": "معرّف العنصر داخل الطلب", "quantity": 1 }],
  "reason": "REFUSED",
  "note": "رفض الزبون هذه القطعة"
}
```

بقيت الحقول customer.instagramUsername وnotes وdeliveryFee وdiscount، والأسعار أعداداً صحيحة آمنة كما في المشروع الحالي. deliveredAmount وreturnedAmount يمثلان قيمة القطع؛ لا توجد سياسة جديدة لتوزيع رسوم التوصيل أو الخصم أو تنفيذ استرداد مالي. التحقق يرفض الحقول غير المعروفة والكميات أو المبالغ غير الصالحة. حد العناصر 100.

## التشغيل والاختبارات

MongoDB يجب أن يكون Replica Set أو Sharded Cluster لدعم المعاملات. الاختبارات تستخدم mongod منفصلاً بقاعدة مؤقتة ومنفذ محلي عشوائي؛ لا تتصل بقاعدة المتجر.

```powershell
$env:MONGOD_BINARY = 'C:\Program Files\MongoDB\Server\8.2\bin\mongod.exe'
node --test tests/orders.unit.test.js tests/orders.integration.test.js
```

تغطي الاختبارات البيع المتزامن لآخر قطعة، تكرار الإنشاء والإرجاع، عدة إرجاعات جزئية، الإرجاع بعد التسليم، منع تجاوز المرسل، تعدد المنتجات، rollback، تعديل الحجز وإلغاءه بالتزامن، والتحقق من صلاحيات HTTP والملكية.

لا تُعدّل هذه الحزمة بيانات الطلبات القديمة. أي طلبات نشأت بمخطط orders-phase1 القديم أو بكميات غير متسقة تحتاج مراجعة مستقلة؛ لا يُعاد بناء المخزون بالتخمين. بصمات مفاتيح قديمة محسوبة على جسم غير مطبّع قد تعطي 409 عند إعادة إرسالها؛ يجب التحقق من الطلب الموجود قبل اعتبار العملية جديدة. لا تعاود إرسال إرجاع ناجح بمفتاح جديد.
